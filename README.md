# Ургийн мод

Гэр бүлийн ургийн бичиг (удмын мод)-ийг бүртгэх, үзэх Django систем.

## Төлөвлөгөө ба шийдвэрүүд

- **Хувийн нэг мод** — олон нийтийн бүртгэл байхгүй, админ/засварлагч мэдээлэл оруулна,
  гэр бүлийн гишүүд урилгаар нэвтэрч харна.
- **Django templates + HTMX + D3.js** — SPA биш, нэг хэл дээр (Python).
- **GEDCOM хэлбэрийн загвар** — импорт/экспортыг дараа нэмэхэд өвдөлтгүй.
- **Django 6.0.7 / Python 3.14.4 / PostgreSQL 16**.

## Өгөгдлийн загварын гол санаанууд

- **Ургийн мод бол DAG, мод биш.** Нэг хүн хоёр эцэг эхтэй, нэг өвөг олон замаар
  ирдэг. Тиймээс `django-mptt`/`treebeard` **ашиглахгүй** — тэдгээр нь нэг эцэгтэй
  модонд зориулагдсан. Холбоог `Family` + `ChildLink` хүснэгтээр илэрхийлж, удмыг
  `WITH RECURSIVE`-ээр бодно (`genealogy/services.py`).
- **`FlexDate`** — бүрэн бус огноо. `raw` (хэрэглэгчийн бичсэн), `qualifier`
  (EXACT/ABOUT/ESTIMATED/BEFORE/AFTER/RANGE/UNKNOWN), `precision`
  (DAY/MONTH/YEAR/DECADE) ба `sort_key` (эрэмбэлэх, нас тооцох)-ыг зэрэг хадгална.
  `FlexDate.parse("ойролцоогоор 1920")` гэх мэт.
  - **`qualifier` нь «ойролцоо» гэсэн тэмдэг — `raw`-д давхар бичихгүй.**
    `display` нь угтварыг (`ойролцоогоор` / `тооцоолсон` / `өмнө` / `дараа`)
    `qualifier`-аас нэмнэ. Хуучин бичлэгт угтвар нь `raw`-д байвал дахин
    нэмэхгүй. Boolean талбар нэмэх нь буруу — `before`/`after`/`range`/
    `estimated`-ыг илэрхийлж чадахгүй.
  - **Бодлого: зөвхөн он.** Амьд хүний яг төрсөн өдөр нь хувийн мэдээлэл тул
    `day`/`month` нарийвчлал **ашиглахгүй** — санд бүх огноо `year` болсон
    (2026-10-04). Профайл дээр ч зөвхөн он харагдана. `lifespan`, модны JSON,
    амьд/нас барсан тооцоо бүгд он дээр ажилладаг тул ямар ч хохиролгүй.
    Ирээдүйд бүтэн огноо оруулах шаардлага гарвал `precision` нь `day`/`month`-ыг
    дэмждэг хэвээр — зөвхөн бодлогоор хязгаарлаж байна.
  - **Оныг хатуу хэлбэрээс үл хамааран шууд тоогоор авна.** Ямар ч танигдсан
    хэлбэр таарахгүй ч текст дотор 4 оронтой он (1000–2099) байвал түүнийг
    авна: `1950?`, `1945~`, `1950 он`, `1950 гэж үзсэн` → бүгд **1950**.
    `?`/`~` нь эргэлзээ илэрхийлдэг тул `qualifier=ABOUT`, бусад нь `EXACT`.
    Он огт байхгүй текст (`баримтгүй`) л `UNKNOWN` хэвээр үлдэж, түүхийг
    хадгална.
- **`ChildLink`** — нэг хүүхэд зөвхөн НЭГ төрсөн гэр бүлтэй (`UniqueConstraint`
  `pedigree='birth'`), гэхдээ олон өргөж авсан гэр бүлтэй байж болно.
- **Цикл хамгаалалт** — `ChildLink.clean()` нь хүн өөрийн үр хойшсын эцэг эх болохыг
  хориглоно; CTE-д мөн `path` массив ба `max_depth` хязгаар бий.
- **Нэгтгэл** — давхардсан хүнийг устгахгүй, `merged_into` тавьж холбоог шилжүүлнэ
  (буцаах боломжтой), `AuditLog`-д бүртгэнэ.

## Хүн ба хамаатны холбоо оруулах

Гурван зам бий:

1. **`+ Хамаатан` → «Шинэ хүн бүртгэх»** — хамаатан байхгүй бол шинэ хүн үүсгэж
   холбоно (модны зангилаа дээрх `+` мөн адил).
2. **`+ Хамаатан` → «Байгаа хүнийг холбох»** — аль хэдийн бүртгэгдсэн хүнийг
   хайж олоод холбоно. Шинэ хүн **үүсэхгүй**.
3. **Django admin** — `Family` ба `ChildLink`-ийг гараар засах (олноор, нарийн).

### Төрсөн ба өргөмөл холбоо

`ChildLink.pedigree` нь холбооны төрлийг хадгална: **төрсөн / өргөмөл /
асран хүмүүжүүлсэн / хойд эцэг эх / тодорхойгүй**. Дүрэм:

- Нэг хүүхэд зөвхөн **НЭГ төрсөн** гэр бүлтэй байна (DB constraint).
- Өргөмөл, асран хүмүүжүүлсэн, хойд гэр бүл нь **нэмэлтээр** зэрэг оршино.
- Форм дээр (quick-add, «Байгаа хүнийг холбох») **«Холбооны төрөл»** сонголт
  байна. «Төрсөн» бус төрөл сонговол **тусдаа гэр бүл** үүсч, төрсөн гэр бүл
  хөндөгдөхгүй.
- Профайл дээр эцэг эх, ах дүү, хүүхдүүд нь төрлөөрөө бүлэглэгдэж харагдана
  («Эцэг эх:», «Өргөмөл эцэг эх:», «Өргөмөл хүүхдүүд:» …).
- Модонд өргөмөл холбоо **тасархай шугамаар** зурагдана. «Зөвхөн цусан
  холбоо» сонголт нь тэдгээрийг нууж, зөвхөн төрсөн холбоогоор мод зурна
  (`?bloodline=1`).

Холбох үед систем **цикл үүсгэхийг хориглоно** (хүн өөрийн үр хойшсын эцэг эх
болох гэх мэт) — мөн аль хэдийн төрсөн гэр бүлтэй хүнийг дахин хүүхэд болгохгүй.
Цикл үүсгэх хүмүүс сонголтын жагсаалтад **огт харагдахгүй**, шалгалт нь
`services._link()` болон `views._blocked_for_relation()` хоёрт ижил байх ёстой.

## Нууцлал

**1. Нэвтрэлт — default-deny.** Бүх сайт нэвтрэлт шаардана. `LoginRequiredMiddleware`
нь «зөвшөөрөгдөөгүй бол хоригло» зарчмаар ажилладаг тул **шинэ view нэмэгдэхэд
автоматаар хамгаалагдана** — view бүрд `@login_required` нэмэхийг мартах
эрсдэлгүй. Зөвхөн хоёр view нээлттэй: `accounts:login` ба `accounts:invite_accept`
(урилга хүлээн авагч нууц үгээ тавих хүртэл нэвтрээгүй байдаг). `/admin/` нь
өөрийн нэвтрэх хуудастай.

**2. `Person.visibility` — нэвтэрсэн хэрэглэгчдийн доторх түвшин.**

- `Person.life_status` — LIVING / DECEASED / **UNKNOWN**. Нас барсан огноо байхгүй ба
  сүүлийн 110 жилд төрсөн бол амьд; огноо огт байхгүй бол UNKNOWN (амьд мэт хамгаална);
  `living_override`-оор гараар засна.
- **Дэлгэц дээрх дүрэм:** «амьд» гэсэн badge БАЙХГҮЙ (нэмэлт биш, хасах
  зарчим) — зөвхөн **нас барсан** хүнийг Bootstrap-ийн `secondary` (саарал)
  өнгөөр тэмдэглэнэ: профайлын гарчиг, хүний карт (нүүр/хайлт), профайл дээрх
  гэр бүлийн холбоос, хайлтын жагсаалт, холбох цонх, модны зангилаа
  (`.tree-node.deceased`), admin-ийн жагсаалт. `person.is_deceased` нь
  `life_status == DECEASED`; огноо тодорхойгүй (UNKNOWN) хүн саарал болохгүй.
- `Person.visibility` — **AUTO (анхдагч)** / PUBLIC / FAMILY / PRIVATE.
  AUTO нь: нас барсан → PUBLIC, бусад (амьд, тодорхойгүй) → FAMILY.
  (Аноним хэрэглэгч аль хэдийн юу ч хардаггүй тул PUBLIC нь зөвхөн
  нэвтэрсэн гишүүдийн хүрээнд утгатай.)
- `Person.objects.visible_to(user)` — **query түвшинд** шүүнэ. Template-д нуух нь
  хангалтгүй: `/tree/<pk>/data/` JSON мөн ижил queryset-ийг ашиглана.
- **Медиа файлыг шууд `MEDIA_URL`-ээр үйлчлэхгүй** — `genealogy.views.serve_media`
  эрх шалгана (`?thumb=1` нь жижиг хувилбар). Эс бөгөөс амьд хүний зураг
  нууцлалыг тойрч нээлттэй болно.

**3. Эрхийн загвар — ADMIN / EDITOR / VIEWER** (`accounts/models.py:46-49`).

| Эрх | `can_edit` | `is_admin` | `/admin/` |
|---|---|---|---|
| `admin` | ✅ | ✅ | ✅ |
| `editor` | ✅ | ❌ | ❌ |
| `viewer` | ❌ | ❌ | ❌ |

- **Үзэгч (VIEWER) — модонд нэмэгдсэн хүн БҮРД үзэх эрхтэй.** Хүн нэмэгдэхэд
  `visibility` нь анхдагчаараа `auto` (→ FAMILY) тул нэвтэрсэн гишүүдэд
  автоматаар харагдана; үзэгчээс нуух **цорын ганц** арга бол
  `visibility = PRIVATE`. Энэ баталгааг `ViewerVisibilityGuaranteeTests`
  хамгаална — санамсаргүй «үзэгчид харагдахгүй болчихсон»-оос сэргийлнэ.
- **Засварлагч (EDITOR) — мөр тус бүрээр.** `Person.can_edit_by(user)` нь
  зөвхөн (а) өөрийн нэмсэн (`created_by`), (б) **«Бүх засварлагч засах
  боломжтой»** (`is_open_for_edit`), (в) оруулсан нь тодорхойгүй
  (`created_by` NULL) хүнийг засна. Хамрах хүрээ: профайл засах/устгах,
  хамаатан нэмэх/холбох (`quick_add`, `link_relative`), гэр бүл засах
  (`Family.can_edit_by` — оролцогч БҮР, ө.х. partner ба хүүхэд бүр эрхтэй
  байх ёстой). Формд `partner`/`person` сонголт ч мөн `editable_by`-ээр
  нарийсдаг ба `user` дамжуулаагүй бол **хоосон** (fail-closed).
- **`PersonQuerySet.editable_by` ба `Person.can_edit_by` нь ЯГ ижил дүрэмтэй
  байх ёстой** — `test_editable_by_matches_can_edit_by` үүнийг шалгана
  (доорх `_link` ↔ `_blocked_for_relation` хоёрын адил зарчим).
- Эрхгүй үед **объектын түвшинд 404** буцаана (оршин байгааг задруулахгүй);
  харин глобал эрхгүй (үзэгч/аноним) бол хуучин хэвээр — redirect эсвэл 403.
- `is_open_for_edit` нь **апп-ын формд БАЙХГҮЙ** — зөвхөн admin сайтаас
  тавина. Орлуулга өвгүүд (`Элэнц`/`Хуланц`/`Элэн`) migration-аар нээгдсэн
  (`genealogy/migrations/0003_person_is_open_for_edit.py`).
- **Тэмдэглэл:** засварлагч шинэ хүн нэмэхэд `created_by` автоматаар тавигдана
  (`PersonCreateView`, `services.create_relative`), тиймээс тэр хүнээ
  цаашид өөрөө засна. `created_by` нь `on_delete=SET_NULL` тул хэрэглэгч
  устгавал бичлэг нь «эзэнгүй» болж, бүх засварлагчид нээгдэнэ.
- **Холбогдсон хэрэглэгч (`Person.linked_user`, 1:1).** Амьд хүн бүр нэг
  бодит хэрэглэгчтэй холбогдож болно — тэр хэрэглэгч **зөвхөн тэр хүнийг**
  засна (үзэгч эрхтэй ч гэсэн). Устгах, хамаатан нэмэх эрх **нэмэгдэхгүй**
  (`can_edit_by`/`editable_by`/`visible_to`/`can_view` дөрөвт нь тусгана).
  Холбоог засах хуудаснаас (`person/<pk>/edit/`) удирдана: имэйлээр урилга
  илгээх (editor/admin) эсвэл байгаа хэрэглэгчийг холбох (зөвхөн админ).
  Нас барсан хүнд холбохгүй; **салгах нь зөвшөөрөгдөнө** (эрх багасгаж байна).
  Холбоосыг удирдах нь **глобал `can_edit` шаардана** — эс бөгөөс холбогдсон
  үзэгч өөрийн холбоосыг өөр хүн рүү шилжүүлж эрхээ бусдад өгч чадна.
- **Editor хүсэлт (`EditRequest`).** Засах эрхгүй гишүүн «Засварлагч болох»
  хуудсаар хүсэлт гаргана; админ «Editor хүсэлтүүд» хуудсаас зөвшөөрнө
  (`VIEWER → EDITOR`; `is_staff`/`is_superuser`-ыг ХЭЗЭЭ Ч хөндөхгүй).

## Deployment

Бүрэн удирдамж (Ubuntu 26, nginx, TLS, GitHub) — **[DEPLOY.md](DEPLOY.md)**.

```bash
sudo cp deploy/urgiin-mod.service /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable --now urgiin-mod
```

Гараар (`/etc/systemd/system/` рүү хуулахгүйгээр) ажиллуулах:

```bash
.venv/bin/gunicorn --workers 3 --bind unix:/run/urgiin-mod/gunicorn.sock urgiinmod.wsgi:application
```

Static файл: `manage.py collectstatic` (Whitenoise үйлчилнэ).

### Нөөцлөлт — ЗААВАЛ

```bash
crontab -e
17 3 * * * /home/deploy/django/urgiin-mod/deploy/backup.sh >> /home/deploy/django/urgiin-mod/logs/backup.log 2>&1
```

`OFFSITE_DIR`-ыг өөр диск/сүлжээний байршилд заана. **Ижил дискэн дээрх нөөцлөлт
нөөцлөлт биш.** Сэргээж туршиж үзээгүй нөөцлөлт ч мөн адил.
